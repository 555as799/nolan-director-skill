# 分发方案与开源项目采用记录

本文保留 4.0 阶段的比较数据和采用过程；4.1 的最终实现与最新统计见 README.md、validation/build-summary.json 和 runtime-adoption-review.md。历史 183 卡、25 项测试等数字不是当前总量。

检查日期：2026-10-07。研究的是公开文档和仓库文件，没有安装或运行第三方人物生成技能，也没有把这些仓库当成诺兰一手史料。

本轮进一步检查了 Persona-Skill 的 [roleplay_contract.md](https://github.com/Tomsawyerhu/Persona-Skill/blob/main/skills/persona/references/runtime/roleplay_contract.md) 和 [select_persona_modules.py](https://github.com/Tomsawyerhu/Persona-Skill/blob/main/skills/persona/scripts/runtime/select_persona_modules.py)，以及 Chat-Haruhi 的 [ChatHaruhi.py](https://github.com/LC1332/Chat-Haruhi-Suzumiya/blob/main/ChatHaruhi2.0/ChatHaruhi/ChatHaruhi.py)。前者把角色核心与场景模块分开选择，后者把人物提示与检索到的故事组合。吸收的是机制，下面为本项目独立实现的位置，没有捆绑其代码或角色台词。

| 本轮采用 | 实现位置 | 验证范围 |
|---|---|---|
| 进入角色时加载有实质内容的核心，后续按场景补充 | references/session-core.md、SKILL.md | 已检查文件可达；是否实际保持角色仍需宿主对话验证 |
| 从创作问题选择相关经历与判断，而不是仅匹配同一个词 | references/situations.json、scripts/recall.py | 12 个开发者选定查询的对照记录在 validation/retrieval-comparison.json |
| 原始证据、角色化转述、新建议分开 | research/primary-refinements.json 及构建后的研究卡 | 新细化 6 卡、复核 4 张旧卡的相关段落，均来自已有来源 |

12 题回归中，旧检索在前四项找到指定相关卡的题数为 5；新检索在同一份旧语料上为 12，在细化后的语料上也是 12。该结果用于定位并修复已知问题；题目由开发者选择，不能当独立测试准确率，更不能当生成回答质量成绩。

## 结论

当前客户使用 WorkBuddy，交付独立 Skill 最省维护成本：角色、知识卡、来源和工具放在同一个版本包，客户导入并开启即可开始创作对话。专家是可选的固定聊天入口；它可以使用同一 Skill，不能据此判定“专家没有数据库”。本包 3.2.2 实际已有 171 张知识卡及检索脚本。

智能体是运行中的整体系统；模型负责理解和生成，Skill 提供可重复使用的工作方法与资源，知识库提供材料，专家是产品入口。Skill 和智能体不是互斥类别。使用何种封装不会自动提升底层模型能力，也不等于完成权重训练。

短期采用无后台服务的资料包，沿用客户 WorkBuddy 账号中的可用模型。普通文本读取无需 Python；可用 Python 时启用本地 SQLite FTS5/BM25。没有额外模型 API 密钥、向量服务或独立 GPU。WorkBuddy 自身的模型额度和联网能力仍由客户账号决定。

当多个客户需要统一后台即时更新、账号权限、跨设备项目记忆和服务端运营时，再把公共研究库独立成检索服务，通过宿主实际支持的连接器提供，保持客户项目记忆隔离。当前没有部署该服务，也没有声称本地包具备这些能力。向量检索是否值得增加，应根据真实未命中的同义问题测试决定，不能只为“高级架构”增加云依赖。

## 这次落地的改变

1. 独立 Skill 含完整人格入口，不依赖原专家主 agent 内的一大段角色指令。无需默认专家团。
2. 原资料完整保留；171 张旧卡＋6 张补充卡＋6 张本轮细化卡合为 183 张，来源条目仍为 65。补充事实与旧卡有交叉，不能称为 183 项独立导演亲历。
3. 其中明确归属诺兰的公开自述候选 29 张、其他主创 8 张、创作研究 89 张、原创示例 57 张；检索默认排除原创示例。分类不意味着其余卡没有本人采访，只表示没有逐项结构化为可直接个人自述的经历。
4. 新检索保留说话者、来源状态、事实、原创迁移与边界；超出输出预算时返回可读卡片定位，避免截断半句话冒充完整事实。
5. 文本单卡、目录、JSON 和 SQLite 由同一构建生成；支持文件读取和脚本两种路径。
6. 项目记忆有单独协议：经用户要求保存、采纳状态分开、客户私有文件不进入共享包。

## 与官方包装约定对照

[WorkBuddy 技能开发文档](https://open.workbuddy.cn/docs/skill) 描述 SKILL.md、references、scripts 结构及中英文描述、版本、作者等字段。本包另生成 WorkBuddy 元数据，通用版本只保留标准字段；这只是配置符合性检查，不等于目标客户端成功导入。

[WorkBuddy 技能市场说明](https://www.workbuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Skills-Market) 提供本地上传安装流程。已生成 ZIP 根目录含 SKILL.md 的上传包；若某客户端要求外层技能目录，则使用 portable 包的目录结构。Windows 客户端原生上传、触发率、端到端延时及目标模型创作质量仍待实际验收，不能从静态检查推断。

## 开源与交付

可给客户分发 Skill，也可将维护源码发布到仓库；两者不是同一决策。本轮准备可维护源码与完整客户包，没有公开发布、创建市场条目或改变旧分享链接。公开发布时为新代码与研究数据分别明确授权范围，保留用户原有素材权属和第三方来源标注，不把书籍、采访或剧本全文装进代码许可证。
