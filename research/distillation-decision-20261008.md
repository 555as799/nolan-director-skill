# 人物资料提炼与模型训练的采用决策

核查日期：2026-10-08（Asia/Shanghai）。范围限定为 RoleLLM、Character-LLM 两项作者发布资料，并与本项目已复核的 Persona-Skill、immortal-skill、ChatHaruhi 对照。本次没有运行上游训练、生成收费 API 请求、下载权重或引入上游人物数据，不声称复现论文效果。

## 决策

当前客户交付继续采用 **WorkBuddy 宿主模型 + 人物 Skill + 可核查经验资料 + 按需检索 + 项目续谈**。本项目目前没有接入可训练的宿主模型权重或独立模型服务；把其他项目的训练代码放进 ZIP 不会改变这一点。

这次值得落地的是：在既有对照测试中，核验**真实经历是否改变了对眼前作品的具体建议**。无需再叠加一个训练框架。只增加片名、第一人称和人物口头禅，不能证明人物能力得到提升。

阅读时，当前 `session-core.md` 已有六项带事实依据及适用边界的常驻判断偏好，包含时间体验、结构与情感、相机位置、演员探索、文学时间组织、制作条件变化；已有卡片区分历史事实、当前迁移和不能推出的结论。这已落实上一份上游复核建议的核心方向。是否改善 WorkBuddy 的真实回答，仍由目标宿主对话结果决定。

Character-LLM 的实际生成器把 API 输出非空作为 `check_result`，随后转换器组织场景、说话人和对话，另加入幻觉相关样本。**输出非空不是史实核验**：这份实现没有在上述函数中建立“诺兰确实经历过这件事”的来源验证。对真实导演顾问，不能把合成的回忆当作亲历。其 README 提供的训练命令需要基座模型，使用 8 个进程；作者给出的 GPU 时间说明不能移作本项目训练完成或效果达标的证据。

本节没有复制人物样本、长段论文内容或训练代码。只读取上述指定文件与论文摘要，没有完整审计上游训练系统，也没有逐项检查论文全部实验。

## “蒸馏”应分清三件事

1. **证据提炼为 Skill。** 把公开访谈整理成常驻判断偏好、经验卡、表达规则和检索导航。改变的是给宿主模型的材料与工作方式，不更新模型参数。本项目正在做这一类。
2. **生成示范或评测数据。** 模型可以帮助生成创作练习和候选回答，但它们必须标为合成内容，与真实采访事实分开；生成数量不能当作新增真实经验。现有项目的原创示例与真实经历分型正是这个边界。
3. **参数训练或模型蒸馏。** 以示范、教师输出或其他训练目标更新可控模型参数，需要指定模型、训练配置、数据权限、算力、评测与部署路径。RoleLLM 的角色条件微调和 Character-LLM 的训练属于这一侧。监督微调也不能未经说明就等同于采用教师 logits 的蒸馏。本项目没有完成这一步。

前两项可以让一个 Skill 更有用，但不能据此声称已经训练出新的“诺兰模型”。第三项也不天然比强宿主模型配合可靠资料更好，需要同条件比较后决定。

## 与已研究的人物 Skill 路线怎么衔接

[既有固定版本复核](upstream-review-20261008.md) 已覆盖 Persona-Skill 的常驻人格与按情境模块、immortal-skill 的证据合并、ChatHaruhi 的角色/相关记忆/对话历史分开组装。本轮训练框架研究没有推翻这些选择：它们位于不同层次，不需要全部同时成为运行依赖。

本项目应继续独立实现并验证这些机制；不导入另一人物的行为习惯、不将模板中的强制五栏答复变成常规对话，也不将生成回忆混入本人经历库。框架数量不是质量指标。

## 发布前最小验证项

对同一组此前未用于修改规则的创作题，分别比较通用协作原则、人物核心、人物核心加相关经验；记录宿主和可见模型信息，若只能用代理模型须明确标出。评审不看配置名称，逐项检查：

- **人物判断有贡献：** 哪一项具体取舍依赖了有证据的公开工作偏好？删除片名和第一人称后，这个区别是否仍然存在？
- **经验有迁移：** 提到的经历是否准确、是否说明与当前制作条件的相同与不同，并实际改变场景或工作方案？
- **对话可推进：** 创作开场直接进入问题，能保住作者的诗性意图；作者只改局部时只推进受影响部分，不重新上课。
- **没有伪造经历：** 找不到本人谈过的书、私事或现场细节时，不借合成内容填补；创作建议仍可继续。

这是发布评估建议，不能把本文件存在当作这些测试已经通过。当前版本的完成程度，应以实际测试记录和客户宿主中的表现报告为准。
